# WEB-R2 loading-boundary experiment (cloud container, 2026-10-21, runtime agent; final report lost to a usage limit, PROGRESS.md and analysis files intact)
Raw: run/boundary/PROGRESS.md, analysis-main.md, analysis-run2.md, results.jsonl, results2.jsonl, run.cjs, analyze.cjs.
Setup: production builds (next build/next start, Next 16.2.7 Turbopack) of byte-identical web source except the variant change, local stack, Chromium 141 headless 1440x900, 4-CPU Linux container, 5 samples per cell, builds interleaved with rotated order and one discarded warm-up each. A = repo build :3000; D = unmodified copy (control, matched A); B = both loading.tsx deleted; C = tab routes moved into a (tabs) route group; E = loading files kept, React throttle constants patched to 0 in built output only; F = project loading.tsx moved one level up to p/loading.tsx; G = project loading.tsx deleted and an explicit <Suspense fallback={same skeleton}> around {children} in p/[project]/layout.tsx.
Which React runs: Next 16.2.7 App Router executes its compiled React 19.3.0-canary-3f0b9e61-20260317 (next/dist/compiled), not react 19.2.4 from package.json; the production client chunk contains the retry-lane reveal throttle (FALLBACK_THROTTLE_MS = 300); Fizz's streamed $RC reveal batch also waits ~300 ms after first paint/last reveal.
Mechanism (layout-router.js): the parent segment's loading module wraps each CHILD segment in a Suspense keyed by the child segment, so switching project tabs (overview -> data -> sites -> forms) mounts a new boundary, commits its fallback, and the content reveal (retry lane) is held until fallback time + 300 ms. Moves within one tab (data -> observation, sites -> site, site -> zones) keep the boundary and never show the fallback.
Warm results (click -> usable, median (min-max), n=5): A 327-360 ms on overview->data, data->sites, site->forms, zones->forms, forms->sites (usable 215-275 ms after the RSC response ended); B 77-221; E 71-216 (fallback still shown, content within 6-19 ms of RSC end); C 329-359 (no improvement); F 79-205 and G 74-201 (fallback never shown). Control rows (data->observation, sites->site, site->zones) ~100-190 ms in every build.
Cold results (fresh context, usable / LCP medians): A overview 338-371 / 384-404, data 371-419 / 428-472, sites 302-312 / 336-348, zones 329-354 / 376-400. B usable 102-232 but first paint later (TTFB 74-179, FCP=LCP 176-308; no early shell flush), LCP better than A by ~100-180 ms. E cold 185-272 usable. F and G cold unchanged vs A (the hard-load fallback is still streamed and the 300 ms Fizz batch still applies).
Conclusion: hypothesis CONFIRMED for warm navigation; the cause is React 19.3's 300 ms fallback reveal throttle triggered by remounting the loading boundary on every tab switch. Smallest real-repo fix: move web/src/app/(app)/o/[org]/p/[project]/loading.tsx up to p/loading.tsx (or replace it with an explicit Suspense inside the project layout) and treat the org (org)/loading.tsx the same way; keeps the skeleton for hard loads, removes the ~250 ms warm floor. Cold-load floor is a separate trade-off (skeleton early vs content ~100-180 ms sooner) and not a defect.
